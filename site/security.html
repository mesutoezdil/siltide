What it reads, and what never leaves the machine

The program watches devices. It does not change them, and it has nowhere to send what it sees unless you configure one.

What it reads

devices

Vendor libraries and tools

NVML and the macOS frameworks are loaded at run time; the other vendors are read from their CLI or from /sys. Nothing is executed with a shell, and every argument is a fixed list rather than a string.

processes

/proc, for names and owners

A process on a device is resolved through /proc to its command, its user and its cgroup, which is how it reaches a container and a pod. Nothing is written there.

kubernetes

Pods, read only

From /var/log/pods, the kubelet pod-resources socket, or the API server with whatever credentials are already on the machine. siltide never writes to a cluster: there is no code in it that can.

disk

Two directories, both yours

Config under ~/.config/siltide, and history, bookmarks and the session under ~/.local/state/siltide. Deleting those two leaves nothing of siltide behind.

What leaves the machine

Only what you asked for, and nothing at all by default. There is no telemetry, no update check and no analytics in siltide, and no code that would report one.

If you configureThen siltide connects to
--listennothing outbound; it accepts connections, and off loopback it requires TLS and a token unless insecure is set
nodes:the siltide services or SSH hosts you listed
alerts:the webhook, Slack URL or Alertmanager you gave it
kubernetesthe API server your kubeconfig or service account already points at
--mcp-httpnothing; it listens on loopback only and refuses any other address

Tokens and TLS

The API token can be stored as a SHA-256 digest, so the plaintext never sits in a config file, and it is compared in constant time. Listening on anything other than loopback without TLS and a token is refused rather than warned about.

Reporting something

A vulnerability should not be a public issue. SECURITY.md in the repository says how to report one, and what happens next.
